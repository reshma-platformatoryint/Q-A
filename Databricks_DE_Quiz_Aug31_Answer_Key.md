# Answer Key — Databricks Data Engineer Practice Quiz — Aug 31

| # | Correct Answer | Short Rationale |
|---|---|---|
| Q1 | **A** — `df.writeStream.foreachBatch(upsert_function).start()` running a MERGE INTO | `foreachBatch` is the standard bridge between Structured Streaming and arbitrary batch write logic (like `MERGE INTO`), which is exactly how upserts are implemented since there's no native streaming upsert sink. |
| Q2 | **C** — `ALTER TABLE my_table SET TAGS ('sensitivity' = 'Confidential')` | Unity Catalog supports applying tags to tables via `ALTER TABLE ... SET TAGS (...)`, which can be run programmatically inside a SQL transformation script. The other options are not valid Unity Catalog / Delta SQL syntax for tagging. |
| Q3 | **C** — `{"continuous": false}` | In the Lakeflow/DLT pipeline settings JSON, the top-level `continuous` boolean controls execution mode. Setting it to `false` switches the pipeline to triggered mode — it processes all currently available data once per run and then shuts the cluster down — which pairs naturally with an external hourly orchestration trigger. The other options aren't valid keys in the pipeline configuration schema. |
| Q4 | **C** — `@dp.expect_or_drop("positive_price", "price > 0")` | `expect_or_drop` flags and silently discards violating rows (without failing the pipeline) while still recording the violation in the event log for tracking — exactly matching "discard invalid records, don't stop the pipeline, log the occurrence." `expect_or_fail` would stop the pipeline, and plain `expect` keeps the bad rows in the table (just flags them). |
| Q5 | **D** — It compares sequence numbers; since Purchase (Seq 90) is older than the current state (Seq 100), LSDP ignores it | APPLY CHANGES INTO uses the sequencing column (not arrival order) as the source of truth for chronological ordering. Since the current stored state already reflects a higher sequence number (100) than the late-arriving Purchase event (90), the older event is correctly ignored rather than incorrectly overwriting the newer "Return" state. |
| Q6 | **C** — `df.groupByKey(...).flatMapGroupsWithState(session_func, OutputMode.Append(), GroupStateTimeout.EventTimeTimeout())` | Custom, arbitrary stateful sessionization logic (tracking open/closed sessions per key with a timeout) requires `flatMapGroupsWithState`, which lets you maintain and update your own state object per key across micro-batches and use an event-time-based timeout to close inactive sessions. `applyInPandas` doesn't maintain cross-batch state, a static join can't track evolving session state, and `lag()` alone can't manage session boundaries/timeouts. |
| Q7 | **A** — Enable `spark.databricks.delta.schema.autoMerge.enabled = true` and use `MERGE INTO ... WHEN MATCHED THEN UPDATE SET * ... WHEN NOT MATCHED THEN INSERT *` | This is Delta Lake's supported mechanism for automatic schema evolution during a `MERGE`: enabling the auto-merge config combined with the wildcard `SET *` / `INSERT *` clauses lets new source columns be automatically added to the target schema. `mergeSchema` (B) is a DataFrameWriter option for direct writes/appends, not for `MERGE INTO` SQL statements. |
| Q8 | **C** — Define a SEQUENCE BY clause using a monotonically increasing column | APPLY CHANGES INTO relies on `SEQUENCE BY` to determine the true order of events for a given key, which lets it correctly resolve duplicates and late-arriving updates by always keeping only the highest-sequence (latest) version of each record — without any manual dedup/groupBy step needed. |
| Q9 | **D** — `.option("startingVersion", 0)` | Setting `startingVersion` to 0 makes the streaming read start from the very beginning of the Delta table's history, so all 2 years of existing data is processed first as the initial batch(es), after which the stream naturally continues with new incoming data. |
| Q10 | **B** — The Event Timeline shows a "waterfall" pattern where most tasks finish quickly but one or two run much longer | This is the classic visual signature of data skew in the Spark UI's Stages tab: nearly all tasks complete fast while a small number of tasks (handling disproportionately large partitions) run far longer, dragging out the stage. The other indicators relate to broadcast joins, empty partitions, or shuffle metrics — not skew specifically. |
| Q11 | **A** — Query `system.query.history`, filtering by warehouse_id and start_time, inspecting statement_text and metrics | `system.query.history` is Databricks' built-in system table that records executed SQL text, duration, and detailed execution metrics (including files-read vs. files-skipped/pruning stats) for queries on SQL Warehouses — exactly what's needed to diagnose this. `DESCRIBE HISTORY` shows table write history (not query execution), `system.billing.usage` shows cost/usage, not query-level detail, and Serverless Warehouses don't expose a traditional Spark UI "Executors" tab. |
| Q12 | **C** — Data within date partitions is randomly distributed regarding sensor_id, causing Min/Max ranges to overlap almost every file | Delta's data skipping relies on each file's Min/Max statistics for a column being tight/non-overlapping so files can be skipped. If sensor_id values are scattered randomly across files within each date partition, nearly every file's Min/Max range will span the requested sensor_id, so the optimizer can't skip files — forcing it to scan almost everything. (Delta *does* collect stats on String columns by default; there's no such disabled-by-default `delta.enableDataSkipping` property; and Spark's Catalyst optimizer pushes filters down regardless of `.filter()`/`.load()` call order.) |
| Q13 | **A** — The view definition is updated; results are calculated using 0.90 on the next evaluation; no physical data is rewritten | Views in Lakeflow Declarative Pipelines are virtual — they store no data of their own and are simply recomputed from their current defining query each time they're evaluated. Updating the hardcoded rate in the view's code just changes what that recomputation uses going forward; there's no stored/incremental state to update and no "Full Refresh" requirement. |
| Q14 | **D** — `readStream.format("delta").option("readChangeFeed", "true").option("startingVersion", 0).load(...)` | Since the Silver table is overwritten in-place (SCD Type 1 via APPLY CHANGES INTO), a plain streaming read can't reliably capture updates. Enabling `readChangeFeed` exposes every insert/update as an appendable change record, and `startingVersion` sets where the stream begins reading from — together enabling a proper incremental read of only the changes. `ignoreChanges`/`ignoreDeletes` merely prevent the stream from erroring on non-append changes; they don't expose the actual updates themselves. |
| Q15 | **D** — `Window.partitionBy("vehicle_id").orderBy("timestamp")` with `F.lag("latitude", 1).over(window)` | `lag()` retrieves the value from the *previous* row within an ordered partition — exactly what's needed to get "the previous ping's" location per vehicle. Partitioning by vehicle_id ensures the lookback stays within the same vehicle, and ordering by timestamp ensures chronological order. `lead()` (option C) would instead fetch the *next* row, and the other options either don't order by time or don't partition by vehicle. |
| Q16 | **D** — `groupBy("region").agg(F.sum(F.when(status=="completed", amount).otherwise(0)).alias(...), F.sum(F.when(status=="failed", amount).otherwise(0)).alias(...))` | Conditional aggregation with `F.when(...).otherwise(0)` inside a single `groupBy("region").agg(...)` computes both pivoted totals in one pass over the data with no extra shuffle or join — the most efficient approach. Option B's `.pivot("status")` is called after `.agg(...)` which is invalid syntax (pivot must be called on grouped data before `.agg()`), and option C requires two separate scans plus a join. |
| Q17 | **D** — `Window.partitionBy("sensor_id").orderBy("timestamp").rangeBetween(Window.currentRow - 300, Window.currentRow)` | A true time-based (event-time) window requires `rangeBetween` on a numeric/timestamp-ordered column, using a window of 300 seconds (5 minutes) back from the current row — this correctly handles irregular/gappy/bursty intervals, unlike `rowsBetween` (options A, B), which counts a fixed number of *rows* regardless of the actual time gap between them. Option C's `rangeBetween(unboundedPreceding, currentRow)` computes a cumulative average from the start, not a rolling 5-minute window. |
| Q18 | **C** — Standalone `normalize_email(df)` and `filter_active(df)` functions, chained via `raw_df.transform(normalize_email).transform(filter_active)` | Defining each transformation as its own top-level, pure function that takes and returns a DataFrame makes each one independently unit-testable with small mock DataFrames, while `.transform()` still cleanly chains them into the full pipeline. Option A bundles both steps into one function (can't test them separately), option B uses inline lambdas (can't be imported/tested independently either), and option D couples the logic inside a class method as one block. |
| Q19 | **B & D** — Liquid Clustering manages data skew via uniform file sizing decoupled from directory structure, and allows changing clustering keys at any time without rewriting existing data | These two capabilities directly map to the two stated problems: (1) skew — because liquid clustering isn't tied to a rigid Hive-style directory-per-key-value structure, it produces uniformly-sized files regardless of how unevenly data is distributed across key values, eliminating straggler tasks; (2) rigidity — clustering keys (e.g., adding `region`) can be changed at any time via `CLUSTER BY`, with new data adopting the new layout immediately and old data reorganizing lazily over time, avoiding a full historical rewrite. (Liquid clustering doesn't enforce PK/FK constraints, doesn't eliminate the transaction log, and doesn't disable data skipping — it actually improves it.) |
| Q20 | **A** — Enable Enhanced Autoscaling in the Lakeflow Spark Declarative Pipeline settings | Enhanced Autoscaling is purpose-built for Lakeflow/DLT pipelines with bursty, variable workloads — it scales up quickly to absorb heavy batch backfills and scales back down aggressively during light streaming phases to control cost, which a standard job cluster's generic dynamic allocation, a high-concurrency/spot setup, or a fixed peak-sized cluster don't do as effectively (the latter in particular wastes cost during the light streaming phase). |
