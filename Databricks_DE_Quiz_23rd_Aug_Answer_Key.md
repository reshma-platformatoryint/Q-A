# Answer Key — Databricks Data Engineer Practice Quiz — 23rd Aug

| # | Correct Answer | Short Rationale |
|---|---|---|
| Q1 | **D** — Lakeflow SDP with Auto Loader and `cloudFiles.schemaEvolutionMode = "addNewColumns"` | Lakeflow Declarative Pipelines manage checkpoints/infrastructure automatically and guarantee exactly-once processing; Auto Loader provides incremental file discovery, and `addNewColumns` handles schema evolution automatically. Manual Structured Streaming (A) requires manual infra management, and static/batch reads (B, C) aren't incremental/streaming. |
| Q2 | **D** — `df.writeStream.foreachBatch(upsert_to_delta).start()` | `foreachBatch` lets you run arbitrary batch logic (a `MERGE INTO`/upsert) against the Delta table for every micro-batch — the standard pattern for upserts in Structured Streaming. The other options aren't real Structured Streaming APIs. |
| Q3 | **A** — Read the change data feed from customer_dim and filter to act on the change events | Because customer_dim is an SCD Type 1 target, its rows are continually updated/deleted in place, which a plain stream can't handle. Enabling and reading CDF on customer_dim exposes each insert/update/delete as an appendable change record, which the downstream job can filter and process incrementally. |
| Q4 | **C** — The source data is valid JSON, but doesn't conform to their defined schema in some way | An explicit schema (`"a int, b int"`) is enforced during read; well-formed JSON that has extra/missing fields or a type mismatch against that schema will still be routed to `badRecordsPath`, even though the JSON itself is syntactically valid. |
| Q5 | **B** — New data is automatically clustered during write operations | Liquid clustering incrementally clusters data as it's written (and via background/OPTIMIZE for further compaction), so new data doesn't sit unclustered waiting on a separate maintenance step. |
| Q6 | **A** — Enable liquid clustering | Liquid clustering handles skew well, lets you change clustering keys at any time without a full rewrite of existing data, and adapts to evolving query filter patterns — unlike Z-ordering/partitioning, which require rewrites when the layout needs to change. |
| Q7 | **B** — `ALTER TABLE my_table SET TBLPROPERTIES ('delta.deletedFileRetentionDuration' = 'interval 15 days')` | This is the supported way to permanently configure how long deleted files are retained for a Delta table. Option A isn't a valid Python DeltaTable API call, option C sets a Spark session config (not a durable table property), and option D (`VACUUM ... RETAIN 15 HOURS`) is a one-time cleanup command, not a persistent retention setting, and uses hours instead of the intended 15 days. |
| Q8 | **B** — Uses the SEQUENCE BY column to order events and retains tombstones until older sequences are processed | AUTO CDC / APPLY CHANGES INTO relies on the `SEQUENCE BY` column (not arrival order) to determine the true chronological order of events, and keeps delete tombstones around so that any out-of-order, older events for the same key are correctly superseded rather than incorrectly reviving a deleted row. |
| Q9 | **B** — Streaming table for raw ingestion + streaming table for incremental "latest per truck_id" + materialized view for daily aggregated reporting | Streaming tables are built for continuous, low-latency incremental processing (ideal for "latest state per truck_id" as new events arrive). Materialized views are efficient for periodic aggregate computations (daily distance/fuel efficiency) and can refresh incrementally without needing continuous low-latency updates. |
| Q10 | **A** — `delta.deletedFileRetentionDuration` is too long (default 7 days), which conflicts with VACUUM | VACUUM will refuse/fail to clean up files younger than `delta.deletedFileRetentionDuration` (default 7 days) as a safety check against removing files that concurrent readers or time-travel queries might still need — so files deleted by MERGE INTO aren't actually removed by a same-duration (or shorter) VACUUM call as expected. |
