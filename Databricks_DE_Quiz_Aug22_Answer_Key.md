# Answer Key — Databricks Data Engineer Practice Quiz — Aug 22

| # | Correct Answer | Short Rationale |
|---|---|---|
| Q1 | **D** — Configure `cloudFiles.maxBytesPerTrigger` with 1GB | `maxBytesPerTrigger` throttles a micro-batch by the total volume of data scanned, regardless of how many files that spans — exactly matching "throttle based on volume scanned at 1GB, regardless of file count." `maxFilesPerTrigger` (C) throttles by file count, not bytes, and `maxPartitionBytes` (B) controls partition sizing for splittable files, not micro-batch throttling. |
| Q2 | **B** — Aggregate total sales per (region, salesperson) first, then `rank()` over `Window.partitionBy("region").orderBy(F.desc("total_sales"))` | Ranking "based on total cumulative sales" requires first computing each salesperson's total (via `groupBy`+`sum`), then applying `rank()` over a window partitioned by region and ordered descending by that total so the highest seller gets rank 1. The other options either compute a running/cumulative sum instead of a rank (A), rank globally instead of per-region (C), or don't order by sales at all (D). |
| Q3 | **D** — Read tasks_status via CDF (`readChangeFeed`), enrich with employee, and use `apply_changes()` into a new streaming table | Because tasks_status is described as storing "the latest status per task" (i.e., rows are updated in place, not purely appended) and has CDF/deletion vectors/row tracking enabled, a plain `readStream()` on it isn't reliable for capturing updates. Reading its change feed captures every insert/update/delete, and `apply_changes()` (AUTO CDC) correctly propagates those enriched changes into the new streaming table incrementally and in near real time. |
| Q4 | **D** — `delta.autoOptimize.optimizeWrite = true` | `optimizeWrite` shuffles/repartitions data *before* it's written so that files are produced at an optimal size right away during ingestion. `autoCompact` (C) instead runs a mini-OPTIMIZE *after* the write (compacting small files post-hoc), which doesn't match "shuffle data before writing." The other two are not real Delta table properties. |
| Q5 | **D** — `CREATE TABLE ... DEEP CLONE prod_catalog.loans ... LOCATION 's3://audit-bucket/loans_2023'` | A regulatory, tamper-proof archive needs its own independent, physically separate copy of the data — that's what `DEEP CLONE` (with an explicit `LOCATION`) provides, unlike `RESTORE` (which mutates the original table in place) or a CTAS/`COPY INTO` (which don't guarantee an efficient, fully independent, versioned snapshot). Conceptually this is the only option that produces an isolated, immutable copy in a separate storage container as required. |
| Q6 | **B** — To prevent deletion of files that might currently be in use by long-running snapshot queries or concurrent streams, ensuring consistency | VACUUM's default minimum retention safety check exists so that files aren't removed while a long-running query, time-travel read, or concurrent stream might still be reading them — deleting too aggressively could corrupt in-flight reads. |
| Q7 | **A & D** — Add a source predicate on the partition column, and enable Low Shuffle Merge | Adding a predicate on a known partition column (if applicable) lets Delta prune partitions and avoid scanning the entire target table, directly addressing the "scanning the entire target table" symptom. Low Shuffle Merge is a purpose-built Delta optimization that reduces the shuffle volume specifically for MERGE operations, directly addressing the "massive shuffling" symptom. A broadcast hint on the *target* (large) side (B) is backwards — you'd broadcast the small side, not the large target — and increasing log retention (C) has no effect on merge performance. |
| Q8 | **B** — Enable Liquid Clustering with initial keys (event_timestamp, user_id) | Liquid clustering lets you change clustering keys later (e.g., add session_id) without rewriting existing data, adapting to evolving query patterns — unlike partitioning or Z-ordering, which require a full or partial rewrite to change the physical layout when query patterns shift. |
| Q9 | **B** — Use Auto Loader (cloudFiles) with File Notification mode | Auto Loader tracks which files it has already ingested via its checkpoint/RocksDB-backed state, so even if the exact same file is uploaded twice, it won't be reprocessed — giving exactly-once file processing "for free" with minimal code. File Notification mode is the scalable, near-real-time discovery mechanism for this. `cloudFiles.allowDuplicates` (A) is not a real Auto Loader option, and the other options require significant custom logic to achieve the same guarantee. |
| Q10 | **B** — `.option("cloudFiles.format", "binaryFile")` | The `binaryFile` format is specifically designed to ingest arbitrary binary files (like images) into a table with a `content` column holding raw bytes plus file metadata columns (`path`, `modificationTime`, `length`) — exactly what's needed here. `"image"`, `"bytes"`, and `"text"` are not valid `cloudFiles.format` values for this purpose. |
| Q11 | **D** — Read the static table as a streaming source (e.g., via `readChangeFeed`) and perform a Stream-Stream join | A plain stream-static join loads the static DataFrame once and caches it, so it won't automatically pick up later changes without a stream restart. Turning the dimension table into a streaming source (reading its change feed) converts the join into a stream-stream join, which continuously and incrementally picks up new/updated dimension rows without ever needing to restart the pipeline. |
