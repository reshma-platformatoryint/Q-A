# Answer Key — Databricks Data Engineer Practice Quiz — 24th Aug

| # | Correct Answer | Short Rationale |
|---|---|---|
| Q1 | **B** — `df.dropDuplicates("unique_key")` with an appropriate watermark enabled | This is the standard Structured Streaming pattern for removing duplicates from a streaming source within a declarative table definition: `dropDuplicates` on the key, bounded by a watermark so state doesn't grow unbounded. `GROUP BY`/`collect_list` (A) is not a valid incremental streaming dedup pattern, `foreachBatch`+MERGE (C) is unnecessary extra complexity for a simple in-table dedup, and the `ignoreChanges` config (D) is unrelated — it's for handling upstream updates/deletes in a streaming read, not deduplication. |
| Q2 | **A & C** — `OPTIMIZE my_table ZORDER BY (customer_id);` **and** `OPTIMIZE my_table;` | Regular `OPTIMIZE` compacts small files (reducing file-listing/scan overhead), and `OPTIMIZE ... ZORDER BY (customer_id)` co-locates data by customer_id within files so Delta can data-skip effectively on that filter column even though the table is physically partitioned by order_date. `VACUUM` (B) only removes stale files for storage cleanup and doesn't speed up queries; `OPTIMIZE ... PARTITION BY` (D) and `ALTER TABLE ... ADD PARTITION` (E) are not valid Delta Lake syntax for this purpose. |
| Q3 | **B** — Add a SEQUENCE BY column to order events and handle update conflicts | `APPLY CHANGES INTO` uses the `SEQUENCE BY` column to determine the true chronological order of change events for a given key. This lets it correctly resolve/ignore duplicate or out-of-order events instead of misapplying them, without needing a manual GROUP BY or an `@dp.view` (views aren't used as CDC targets). |
| Q4 | **C** — Implement a write operation using MERGE INTO with a unique key | Since duplicates can arrive up to a week apart, they'll fall well outside any reasonably sized Structured Streaming watermark, so state-based `dropDuplicates` (B) won't catch them. `MERGE INTO` on the unique key checks against the *entire* existing target table (not just recent state), guaranteeing each record appears exactly once regardless of how far apart duplicates arrive. |
| Q5 | **A** — Delta Lake works with various data formats (Parquet, JSON, CSV) | This statement misrepresents Delta Lake: Delta tables are stored specifically as Parquet files plus a transaction log — Delta itself does not natively store table data as JSON or CSV. (You can *ingest* from JSON/CSV sources, but that's not the same as Delta "working with" multiple storage formats.) The other statements — unified batch/streaming, scalable metadata handling for billions of files, and reliance on partner tooling for monitoring — are accurate descriptions of Delta Lake. |
| Q6 | **A** — `.option("startingVersion", 0)` | Setting `startingVersion` to 0 tells the streaming read to start from the very beginning of the Delta table's transaction log, ensuring all historical data is processed as the initial batch(es) before the stream catches up to new incoming data. The other options aren't valid Delta streaming read options. |
| Q7 | **B** — Use Auto Loader with event notification mode and no additional options | Auto Loader's checkpointing already guarantees exactly-once processing by default, and event notification mode is the efficient, low-maintenance way to detect new files in near real-time at scale — no extra options are needed. The other listed options (`useIncrementalListing`, `allowDuplicates`, a generic `ignoreDuplicates` flag) are either irrelevant to event notification mode or not real Auto Loader/Structured Streaming configuration options. |
| Q8 | **A** — Auto Loader + DLT with an `EXPECT ... ON VIOLATION DROP ROW` constraint combined with record audit logic to route bad records | This is the standard Lakeflow/DLT pattern for quarantining: expectations flag/drop rows that violate data quality rules from the main flow, while accompanying audit/rescue logic captures those same rows into a separate quarantine table — all without failing the job, and works for both batch and streaming Auto Loader ingestion. The other options either can't reliably catch row-level malformed data (B), silently drop data without capturing it (C), or explicitly ignore bad records instead of quarantining them (D). |
| Q9 | **B** — Two separate streaming jobs; quarantine job on a separate small cluster, run once a day | Running the good-data and quarantine-data logic as fully independent streaming jobs keeps the low-latency production stream completely unaffected by the quarantine workload. Putting the quarantine job on its own small cluster with an infrequent (daily) run matches its low-priority, low-cost, occasionally-reviewed nature — unlike combining them (which risks impacting production latency) or sharing a cluster (which couples their resource usage/cost and availability). |
| Q10 | **D** — `@dp.view` will be fully recomputed on the next pipeline update, without affecting the raw_data storage | Views in Lakeflow Declarative Pipelines are virtual (not materialized) — they hold no stored data of their own and are simply recomputed from their defining query whenever the pipeline runs. Updating a view's logic (e.g., adding a calculated column) only changes how it's computed on the next run; it doesn't require dropping/recreating anything and has no effect on the underlying raw_data table's stored data. |
